# Charity Fund — Прозрачная помощь проектам

> **Живой сайт:** [charity.up.railway.app](https://charity.up.railway.app)

Лендинг благотворительного фонда с системой **слотов поддержки**: участник выбирает конкретный слот (нужду фонда), оплачивает его полностью или частично и получает на почту именной сертификат и фотоотчёт.

## Концепция

- **Слот** — конкретная цель помощи с фиксированной суммой (например, «Деревья — 150 000 ₽», «Театральный занавес — 20 000 ₽»).
- **Прозрачность** — для каждого слота видно цель, собранную сумму и остаток.
- **Гибкость взноса** — полностью или частично, разово или ежемесячно.
- **Подтверждение** — именной сертификат и фотоотчёт о помощи.

## Стек

- **Backend** — Node.js 20 + Express, единый контейнер, раздаёт статику и API.
- **БД** — SQLite через `better-sqlite3` (синхронный, быстрый, файловый).
- **Auth** — собственная HMAC-подписанная cookie-сессия, без сторонних библиотек.
- **Frontend** — Vanilla HTML/CSS/JS, без сборки и фреймворков.

Шрифты: **Inter** (UI) и **Cormorant Garamond** (display) из Google Fonts.

## Приём заявок

Форма «Помочь фонду» шлёт `POST /api/apply` с полями
`slot`, `slotTitle`, `participantName`, `email`, `amount`, `frequency`.

Сервер:

1. **Валидирует** входные данные.
2. **Rate-limit** — 10 заявок/мин с одного IP.
3. **Шлёт в Telegram** координатору (если настроено) — мгновенное уведомление.
4. **Сохраняет в SQLite** — для админки, экспорта, истории, статусов.

Если Telegram не настроен или не отвечает — заявка всё равно сохраняется в БД.

## Админка

Открыть `/admin`. Зайти по логину и паролю из env-переменных.

Что умеет:

- **Сводка** — всего заявок, по статусам, общая и регулярная сумма
- **Таблица заявок** с инлайн-сменой статуса (`Новая → В работе → Закрыто / Отклонено`)
- **Фильтры** по статусу + поиск по имени/email/слоту
- **Деталка** заявки в модалке (IP, User-Agent, заметки)
- **Экспорт CSV** для бухгалтерии
- **Сессия** — подписанная cookie на 7 дней, `HttpOnly` + `SameSite=Lax` + `Secure` в проде
- **Защита** — rate-limit на логин (8 попыток / 5 мин), constant-time compare, same-origin check на мутации

## Переменные окружения

| Переменная | Обязательность | Описание |
|---|---|---|
| `PORT` | — | Порт сервера (Railway инжектит автоматически) |
| `DATA_DIR` | опц. | Директория для SQLite. По умолчанию `./data`. На Railway — `/app/data` (там монтируем Volume) |
| `TELEGRAM_BOT_TOKEN` | опц. | Токен бота из [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_CHAT_ID` | опц. | ID чата для уведомлений координатору |
| `ADMIN_USERNAME` | опц. | Логин админа (по умолчанию `admin`) |
| `ADMIN_PASSWORD` | **обяз. для админки** | Пароль админа. Если не задан, `/api/admin/*` отдают 503 |
| `SESSION_SECRET` | рекоменд. | Секрет для подписи cookie (32+ случайных символов). Если не задан, генерируется при старте — сессии сбрасываются на каждый деплой |
| `NODE_ENV` | — | `production` в проде → cookie получает `Secure` |

### Как сгенерировать `SESSION_SECRET`

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

## Хранилище

База — `${DATA_DIR}/charity.db`. Чтобы данные **переживали редеплои** на Railway:

1. В Railway → Service → **Volumes** → **Add Volume**
2. Mount path: `/app/data`
3. Размер: 100 МБ для начала (хватит на десятки тысяч заявок)
4. После создания — Railway передеплоит, файл БД создастся автоматически

Без Volume база живёт внутри контейнера и **сбрасывается на каждый редеплой** — для тестов это OK, для прода нужен Volume.

## Telegram-бот (5 минут)

1. [@BotFather](https://t.me/BotFather) → `/newbot` → получить **TOKEN**.
2. Найти бота в Telegram, нажать **Start** (иначе бот не сможет вам писать).
3. Узнать `chat_id`:  
   `https://api.telegram.org/bot<TOKEN>/getUpdates` →  
   найти `"chat":{"id":123456789, ...}`.
4. (Опц.) Создать приватную группу координаторов, добавить туда бота, использовать `chat_id` группы (обычно отрицательное число).
5. В Railway → Variables → задать `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`.

## Деплой

Прод-окружение: **Railway** → [charity.up.railway.app](https://charity.up.railway.app).
Каждый push в `main` автоматически пересобирается и публикуется.

В корне лежит `Dockerfile` на базе `nginx:1.27-alpine`:

- Слушает динамический `$PORT` от Railway (через nginx-шаблон + `envsubst`).
- Гзип, агрессивный кеш статики (30d, `immutable`), короткий кеш HTML (5 минут — чтобы обновления раскатывались быстро).
- Security headers: `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`.
- SPA-fallback: любая 404 ведёт на `index.html`.

### Запустить контейнер локально

```bash
docker build -t charity-fund .
docker run --rm -p 8080:80 charity-fund
# открыть http://localhost:8080
```

### С кастомным портом (как Railway)

```bash
docker run --rm -e PORT=3000 -p 3000:3000 charity-fund
```

## UI / UX

Подача — премиальная, спокойная: тёплая «бумажная» палитра, угольный hero, золотые акценты, антиквенный display-шрифт.

Микро-взаимодействия:

- Aurora-градиент в hero (CSS, без WebGL)
- Cursor spotlight за курсором
- Magnetic CTA — кнопки «тянутся» к курсору
- Scroll-reveal со stagger-анимацией карточек
- Animated counters в статах героя
- Spring-чипы быстрых сумм
- `:has()`-driven сегментированный переключатель «Ежемесячно / Разово»

Полная поддержка `prefers-reduced-motion` — всё стопорится для тех, кому важно.

## Что уже работает

- Лендинг с премиальным UI и системой слотов.
- Приём заявок через форму с пересылкой координатору в Telegram.
- Хранилище в SQLite — заявки переживают перезапуски (с Volume).
- Админка с авторизацией: сводка, таблица, статусы, поиск, экспорт CSV.

## Что пока НЕ работает (осознанные ограничения)

- **Прогресс слотов на лендинге локальный** — всем посетителям показывается стартовое состояние; «реальный» прогресс будет, когда добавим публичный счётчик из БД.
- **Нет реальных платежей** — это макет UX без интеграции с платёжным шлюзом.
- **Сертификаты и фотоотчёты пока вручную** — координатор отправляет их на email из заявки.
